## Concept understanding

### Understood well
- Ch. 1: Hexagonal architecture, monolithic hell (6 symptoms), scale cube (X/Y/Z axes), microservices as Y-axis decomposition, database-per-service rationale, pattern language structure (forces / resulting context / related patterns)
- Ch. 2: 4+1 view model (logical/implementation/process/deployment/scenarios), hexagonal architecture (inbound/outbound adapters and ports), three-step architecture process (system ops → services → APIs), decompose by business capability, decompose by DDD subdomain, SRP and CCP applied to services, god class problem and resolution via per-service domain models, bounded context = service boundary, Ubiquitous Language per service (Order vs Ticket vs Delivery)

- Ch. 5 (read directly from the book, pages 146–182): business logic organization patterns — transaction script (procedural, one method per system operation; this is what `TicketService`/`SagaJoinService` looked like pre-refactor) vs. domain model (behavior lives in the entities); DDD as a refinement of the domain model approach, not a third alternative. The three aggregate rules: (1) reference only the aggregate root, (2) inter-aggregate references use primary keys not object references (already true throughout this codebase, e.g. `Order.consumerId`), (3) one transaction creates/updates exactly one aggregate — the formal justification for *why* sagas (Ch.4) exist at all. Aggregate granularity trade-off: fine-grained (better concurrency, more sagas) vs. coarse (fewer sagas, more lock contention) — book recommends fine-grained by default. Domain events: the book's preferred mechanism is an aggregate method returning `List<DomainEvent>` to the calling service (over an `AbstractAggregateRoot`-style superclass, which couples aggregates to a base type); event enrichment (stuffing extra fields into events so consumers don't need a callback query) trades event stability for consumer simplicity. The book's own worked examples for this chapter are `Ticket` (Kitchen Service) and `Order` (Order Service) — the same two candidates already flagged in this project on 2026-07-18, now confirmed as the book's actual choice, not a coincidence. The `Order` aggregate refactor itself (state machine in Fig. 5.14, paired methods per saga step like `revise()`/`confirmRevision()`) is now fully applied to this codebase, along with `Ticket` and — going one step beyond the book's own two named examples — `Authorization` (accounting-service), so "reverse"/"revise" are real guarded transitions there too, not unguarded status-string mutations.
- Ch. 6 (event sourcing): an event store is a hybrid of a database and a message broker — it's both the durable system of record (replayable events, replacing a row-per-aggregate table) and, via CDC on the same append-only log, the delivery mechanism for the events other services need. The `process(Command)`/`apply(Event)` split is the core discipline: `process()` validates and decides what happened (pure, no mutation), `apply()` unconditionally mutates state given an event that already happened (used both for the just-decided event and for every historical event during replay) — collapsing them (deciding and mutating in one step) is the mistake that makes replay impossible. Snapshots are a pure performance optimization (avoid replaying arbitrarily many events for aggregates with a long history) with no effect on correctness — this codebase implemented them anyway for `Order` despite its short lifecycle, purely for the learning exercise. Optimistic concurrency control is still required with event sourcing (two concurrent commands against the same aggregate version must not both succeed), it just moves from a `@Version` column on a mutable row to a version count on the event stream itself — this codebase used a dedicated version-tracking table rather than deriving the version from `COUNT(*)` on the event table, so the two concerns (how many events exist vs. what version an update is conditioned on) stay independently reasoned about. The subtlest lesson, learned the hard way rather than read: not every row that shares an event-sourced aggregate's storage table is a replayable domain event — a wire-only pseudo-event smuggled onto the same table for CDC convenience will silently break every future replay unless the store explicitly distinguishes "happened to the aggregate" from "needs to reach Kafka." For orchestration-mode sagas, the book's actual mechanism is genuinely more machinery than the "just publish in the same transaction" shortcut: a `SagaCommandEvent`-style pseudo-event (here, `OrderSagaCommandRequest`, a dedicated table separate from the real event log) plus a poller, mirroring the same outbox-publish discipline used for real domain events — chosen deliberately over the shortcut specifically to see the book's actual mechanism, not because the shortcut would have been wrong.
- Ch. 7 (implementing queries): the book frames API composition and CQRS as two genuinely different answers to "how does a client get a view spanning multiple services' data," not two versions of the same idea, and this project implemented both rather than picking one, specifically to see the tradeoff rather than read about it. API composition (`GET /orders/{id}/view` on order-service) assembles a response at request time from four live parallel calls (restaurant/kitchen/accounting/delivery-service, each via Eureka discovery + circuit breaker), trading latency and availability coupling to those four services for always-current data; a `SectionResult<T>` (`Found`/`NotFound`/`Unavailable`) per section means one degraded downstream degrades its own section, not the whole response. CQRS (`GET /order-views/{orderId}` on the new standalone `ftgo-order-history-service`) maintains a standing, pre-joined read model built incrementally from the same domain events every saga participant already publishes, trading eventual consistency and a dedicated extra service/datastore for near-instant, fully decoupled reads — this service has no Eureka registration and is reachable only via Kafka, since its own availability must never depend on (or be depended on by) any write-side service. A real concurrency bug surfaced the actual cost of CQRS's "just consume events and upsert" simplicity: because `OrderView`'s `@Id` is externally assigned, every `save()` goes through `EntityManager.merge()` (a full-column UPDATE, not dirty-checked), so four independent `@KafkaListener` consumer threads racing to update the same row could silently lose an update without `@Version` optimistic locking — the same pattern `ftgo-accounting-service`'s `SagaJoinState` already used for a different reason (exactly-once join resolution), now reused here for a different one (lost-update prevention across independent topics).
- Ch. 8 (API gateway / BFF): the book's two gateway patterns — a single shared API gateway vs. one gateway per client type (Backends for Frontends) — aren't presented as competing choices to pick one of, they're the same underlying pattern (an edge service fronting the backend services) applied with a different ownership/scoping decision; this project implemented the BFF variant (`ftgo-mobile-gateway`, `ftgo-public-gateway`), each independently configured (its own API key, its own rate limit) and independently deployable, per the book's ownership rationale. The gateway-level composition the mobile gateway does (`GET /mobile/orders/{orderId}`) is architecturally the same idea as Ch.7's API composition (assemble one response from several services' data, degrade gracefully per-section via a `SectionResult`-shaped type) but performed one layer further out — at the edge, in front of the services, rather than inside one of the services being composed — and the two now deliberately coexist rather than one replacing the other, since they serve different callers with different freshness/ownership needs. The single most important lesson, learned only by building it, not by reading about it: Spring Cloud Gateway's filter chain (`GlobalFilter`s, route-level `GatewayFilterFactory`s) is scoped to requests matched by a declared `RouteLocator`/YAML route — a hand-written WebFlux `RouterFunction` bean in the same application is dispatched by an entirely different mechanism (`RouterFunctionMapping`) and never sees that filter chain at all, so any cross-cutting concern (auth, logging, rate limiting) needed on a RouterFunction-based endpoint has to be applied by hand, endpoint by endpoint — a real, non-obvious operational gap this project deliberately left parked (no rate limiting/logging on the mobile gateway's composed endpoint) rather than silently ignored.
- Ch. 9 (testing strategies, unit testing): the test pyramid (unit at the base, fewest end-to-end tests at the top) and the solitary/sociable distinction — entities, value objects, and sagas get *sociable* unit tests (test the class together with its real, cheap-to-construct dependencies, e.g. an `Order` built via its own real constructor/methods, not mocked), while domain services, controllers, and event/message handlers get *solitary* unit tests (mock the collaborators — repositories, publishers, other services — and verify the class's own dispatch logic in isolation). The most useful finding wasn't a new technique to learn, it was discovering this codebase had already converged on 4 of the book's 6 named patterns without ever having read the chapter — evidence that the DDD-aggregate work from Ch.5 and the domain-service/controller/listener separation from every chapter since had already been shaping tests toward exactly this structure. The two real gaps found were both about assertion *depth*, not technique: several saga-orchestrator and message-handler tests verified that a call happened but not that its payload was correct (a trailing Mockito `any()` where a real value was available), which is the same class of blind spot a wrong-field regression could slip through silently.
- Ch. 10 (testing strategies, remaining patterns): consumer-driven contract tests (§10.1, `ftgo-order-service` as producer verified against a Pact broker-hosted contract, `ftgo-kitchen-service` as consumer publishing the same contract) sit one level above unit tests in the pyramid — they verify the *shape* of a cross-service interaction without standing up either service's full stack, catching the specific class of bug (a renamed/removed field breaking a consumer that was never run against the real producer) that solitary unit tests structurally cannot see. Component tests (§10.2, Cucumber + Spring Boot `@SpringBootTest` against one service's real Spring context with only its external dependencies — Kafka, MySQL — stood up via Testcontainers) test one service's full internal wiring (controllers → domain → outbox → Kafka) without the cost or flakiness of the entire multi-service stack. End-to-end tests (§10.3, this session) sit at the top and are deliberately minimized in number: one Cucumber scenario driving a full Create→Revise→Cancel Order journey through the real `ftgo-public-gateway` against the entire Docker Compose stack (all 7 business services + both gateways + infra), the only test level in this codebase where a saga's cross-service choreography is observed from the outside exactly as a real client would see it, rather than asserted against internal state or a single service's own contract. The revise-decline step doubles as an accounting-service domain fact worth keeping straight: `Order.rejectRevision()` returns status to `APPROVED`, not `REJECTED` (that status is reserved for a declined *initial* CreateOrder authorization), so a declined revision is only observable via the line items reverting to their pre-revision quantity — the test asserts on quantity, not status, for exactly this reason. The decline trigger itself is `SagaJoinService.isAuthorized(totalQuantity)`, approving iff total line-item quantity ≤ 10 — the scenario places quantity 2 (approves) then revises to quantity 12 (declines) to exercise both branches with one saga run. `SAGA_MODE=orchestration` was the deliberate choice for this suite (an env override on top of the compose file's `choreography` default), to exercise the CreateOrderSagaOrchestrator/CancelOrderSagaOrchestrator/ReviseOrderSagaOrchestrator path at least once under full-stack conditions, since the choreography path was already covered by earlier chapters' Docker verification.

### Architecture decisions made
- Hexagonal layers as Java packages (not Gradle sub-projects) — matches reference impl, simpler
- Shared `ftgo-common` module (2026-07-18) — extracted the generic outbox/dedup infrastructure (OutboxEvent, ProcessedEvent, their repositories, OutboxPublisher, KafkaProducerConfig) into a new Gradle module, `com.sanjay.ftgo.common.outbox`, depended on by all four saga services. The saga wire-format records (SagaReply, KitchenCommand, ConsumerVerificationEvent, etc.) remain per-service, copy-pasted into every producer/consumer — deliberately out of scope for this pass, since those carry business meaning specific to who produces/consumes them rather than being generic plumbing. Each service now carries a small `PersistenceConfig` class (rather than annotating the `@SpringBootApplication` class directly) with `@EntityScan`/`@EnableJpaRepositories`/`@ComponentScan` all pointed at both the service's own domain package and `com.sanjay.ftgo.common.outbox` — putting those annotations directly on the application class broke `@WebMvcTest` slice tests (order-service's `OrderControllerTest`), since annotations on the primary configuration class bypass slice-test type filtering in a way a separate `@Configuration` class doesn't.
- Minimal dependencies per service (web, jpa, mysql, test) — Eventuate Tram added in Ch. 3
- Single MySQL instance, one schema per service — lower local overhead, matches Richardson's Compose setup
- H2 in test scope with MODE=MySQL — allows contextLoads tests without a running DB

### Code patterns implemented
- DDD aggregate (2026-07-20) — `Ticket` (kitchen-service): `TicketState` enum with enforced legal transitions, class-per-event domain events behind a sealed `TicketDomainEvent` interface, returned from state-changing aggregate methods rather than hand-built inline in the service layer. `TicketDomainEventPublisher` translates typed domain events back into the pre-existing flat `KitchenEvent` wire record before writing to the outbox, preserving exact wire-format compatibility with `order-service`'s existing consumer (no new fields ever leak onto `kitchen.events`, since Jackson's default strict unknown-property handling would break deserialization there).
- Event sourcing (2026-07-22/24) — `Order` (order-service): `OrderAggregate` implements the book's `process(Command)`/`apply(Event)` split (9 command types); `OrderEventStore` is the hand-rolled event store (append-only `order_events` table, `replay()` reconstructing an aggregate from a snapshot plus the tail of events since it, `update()` combining a version-row optimistic-lock check with append-and-apply in one transaction); `OrderSnapshot`/`OrderSnapshotData` capture aggregate state every 5 events purely for replay-cost amortization, with zero effect on correctness; a dedicated `order_aggregate_version` table (not derived from event count) backs optimistic locking, mirroring the JPA path's `@Version` column but as an explicit row Hibernate's own dirty-checking flush (not `merge()`) performs the check against. An `OrderTransitions` facade abstracts the JPA/event-sourced choice from every call site; a parallel `SagaCommandPublisher` facade does the same for orchestration-mode saga commands, backed in event-sourcing mode by `OrderSagaCommandRequest` (a table deliberately separate from `order_events`) and a `SagaCommandRequestPublisher` poller — the book's actual pseudo-event mechanism rather than a same-transaction shortcut. One hard-won lesson from this pattern, not obvious from the book text: a table doubling as both an event-sourcing replay log and a CDC transport (as `order_events` does here) needs an explicit flag distinguishing the two, or a wire-only pseudo-event smuggled in for CDC convenience alone will corrupt every future replay of that aggregate.
